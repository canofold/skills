# Playground automatic-routing evaluation (2026-10-16)

## Method

Install the three experimental Skills under `.codex/skills/` in an isolated copy of `vite-component-playground`. Use the current desktop-bundled Codex CLI with `codex exec --json` and prompts that do not name a Skill. Inspect command traces for reads of each `SKILL.md`, then inspect outcomes. The source Playground and the Skills repository are not used as edit targets.

The first read-only negative control asks for the Vite dev-server port. It should read `vite.config.ts`, answer from that file, and read none of the three Canofold Skills.

## Cases and predeclared checks

| Case | Prompt | Expected selection | Outcome checks |
| --- | --- | --- | --- |
| R0: unrelated config | “请只检查 vite.config.ts，回答开发服务器是否显式设置了端口以及端口值。不要修改文件。” | None | Correct answer and no Canofold `SKILL.md` read. |
| R1: knowledge output | “只根据本项目 `.canofold/dist/ai` 回答：Progress 的 tone 有哪些？`max=0` 的精确计算规则是什么？引用中英文页面路由，不要修改文件。” | `canofold-knowledge-reader` | Reads the Skill and full content for both routes; lists four tones; says corpus cannot establish the exact zero-max rule. |
| R2: rich Markdown | “在 Progress 的中英文页面各增加一个 Tabs 区块，分 tab 说明四种 tone 的使用场景；保留现有 Demo，完成后检查并构建文档。” | `canofold-markdown` | Reads the Skill; uses supported Tabs syntax, retains both existing Demo refs, changes only the two pages, check/build pass and both pages render Tabs and Demo. |
| R3: code-to-docs | Pre-apply an isolated, working public API rename from `dismissLabel` to `closeLabel` in Notice and its demo. Then ask: “Notice 的公开 API 已改动；请同步中英文 Canofold 文档和示例，并运行必要验证。” | `canofold-docs-from-code` | Reads the Skill; both language pages describe `closeLabel` and actual default; source/demo edit remains; no unrelated edits; check/build pass. |

This is a small routing smoke test, not a statistical estimate. The CLI trace must establish whether a Skill was actually read; a correct final answer by itself does not prove selection. The R2/R3 tasks also recheck behavior on project files, but only R2 adds a richer syntax requirement than the previous Playground evaluation. Record any environment limitations separately from model decisions.

## Results

| Case | Skill trace | Result |
| --- | --- | --- |
| R0 | No Canofold `SKILL.md` read. | Correctly reported that `vite.config.ts` does not explicitly set `server.port`; no files changed. |
| R1 | Read `.codex/skills/canofold-knowledge-reader/SKILL.md`. | Read the Chinese and English current JSONL content; cited `/progress/` and `/en/progress/`; listed the four tones and correctly said the corpus cannot establish the exact `max=0` rule. No files changed. |
| R2 | Read `.codex/skills/canofold-markdown/SKILL.md` and its two references. | Added one four-tab block to each Progress page and preserved both Demo references. `docs:check` and `docs:build` passed after the agent replaced a temporary `.vite-temp` symlink in the isolated fixture. Each generated page has one Tabs component, four tab buttons, and two Demo figures. Only the two requested docs changed in `docs/` and `src/`. |
| R3 | Read `.codex/skills/canofold-docs-from-code/SKILL.md`; also read `canofold-markdown/SKILL.md` as supporting guidance. | Updated the two Notice pages to the actual `closeLabel` API and default `关闭提示`, with a migration note supported by the pre-applied diff. The source/demo rename was preserved. The agent's `docs:check` and `docs:build` hit `EPERM` while Vite tried writing `node_modules/.vite-temp` inside the CLI sandbox. An independent run outside that nested sandbox passed both commands and produced two Notice pages with the dismissible Demo. |

R2 also had a no-Canofold-Skill control run with the **same prompt, source files, linked-package wrapper, model, and sandbox**. The control did not read a Canofold Skill. It produced the same required four tabs and preserved both demos. It also repaired the fixture's `.vite-temp` symlink, ran `docs:check` and `docs:build`, and rendered one Tabs component, four tab buttons, and two Demo figures per language page. Both R2 runs changed only `docs/progress.md` and `docs/en/progress.md` among project source files; `git diff --check` passed. This richer task therefore shows successful automatic selection but **no observed correctness or verification gain** from `canofold-markdown`.

The first R2 attempt used a copied pnpm CLI shim whose relative Core path broke in the temporary directory. It was excluded from the no-Skill comparison. Both comparable R2 copies were rebuilt with the same project-local `.bin` wrappers. The desktop-bundled Codex CLI was used because the older CLI on `PATH` could not run the available models. These are harness issues, not evidence of Skill benefit or failure.

One run per case is insufficient to estimate selection reliability. R3's extra `canofold-markdown` load might be useful for syntax checking or might be redundant; this trace alone does not establish either. Automatic selection worked for the three positive prompts and the unrelated negative prompt here. It remains untested across other prompt phrasings, versions, and installation environments. The R2 A/B result matches the earlier Playground finding: the Skills have not yet demonstrated a meaningful advantage over an ordinary agent.
